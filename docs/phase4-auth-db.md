# Phase 4 · 계정과 데이터베이스 설계

이 문서는 구현 전에 결정해야 할 것을 정리한 것입니다. 승인 후 구현에 들어갑니다.

## 요약

- **Supabase**(Postgres + Auth)를 씁니다. 무료 티어로 충분합니다.
- **사이트는 계속 정적으로 둡니다.** 서버 렌더링 전환은 Phase 4에 필요 없습니다.
- 보안은 애플리케이션 코드가 아니라 **DB의 행 수준 보안(RLS)** 이 강제합니다.
- 로그인 전에 브라우저에 쌓인 기록은 로그인 시 서버로 **합칩니다.** 지우지 않습니다.

---

## 1. 서버 렌더링이 필요 없는 이유

앞선 논의에서 "로그인을 넣으려면 Astro를 서버 모드로 바꿔야 한다"고 적었는데,
다시 확인해 보니 **Phase 4·5에는 필요 없습니다.** 정정합니다.

개인화 화면은 이미 전부 브라우저에서 그려집니다. `/my`는 `client:only`이고,
저장 버튼도 클라이언트 컴포넌트입니다. Supabase 클라이언트는 브라우저에서
직접 DB와 통신하며, 남의 데이터 차단은 서버 코드가 아니라 RLS가 맡습니다.

따라서 이 단계에서는

- 어댑터 설치 없음
- 서버리스 함수 없음
- 개념 페이지 53개는 지금처럼 정적 HTML 유지 (SEO·속도 그대로)

서버가 필요해지는 시점은 **Phase 6(AI 문제 생성)** 입니다. Anthropic API 키가
브라우저로 가면 안 되기 때문입니다. 그때 Vercel 어댑터를 추가하고 **해당
엔드포인트 하나만** 서버 렌더링으로 표시하면 됩니다. 나머지는 계속 정적입니다.

## 2. 왜 Supabase인가

| 후보 | 판단 |
|---|---|
| **Supabase** | Postgres·인증·보안정책이 한 서비스. RLS로 데이터 격리를 DB가 강제. 무료 50,000 MAU / 500MB. 패키지 하나(`@supabase/supabase-js`) |
| Clerk + Neon | 인증 UX는 낫지만 서비스가 둘로 늘고, 권한 검사 로직을 직접 짜야 함 |
| Vercel Postgres + Auth.js | Astro 연동 배선이 많고 무료 용량이 더 작음 |

혼자 운영하는 서비스에서 **권한 검사를 직접 짜지 않아도 되는 것**이 가장 큰 이점입니다.
코드에서 `where user_id = ...`를 빠뜨려도 DB가 막아 줍니다.

비용은 당분간 0원입니다. 무료 한도를 넘길 규모가 되면 그때 유료 전환을 검토합니다.

## 3. 로그인 방식

**이메일 매직 링크**를 기본으로 하고, **Google 로그인**을 함께 제공할 것을 권합니다.

- 비밀번호를 아예 다루지 않습니다. 유출될 비밀번호가 없는 것이 가장 안전합니다.
- 학생 사용자에게 가입 절차가 짧습니다.
- 카카오 로그인도 Supabase가 지원하므로 나중에 추가할 수 있습니다.

## 4. 테이블

전체 DDL은 [`supabase/migrations/0001_init.sql`](../supabase/migrations/0001_init.sql)에 있습니다.

지금 필요한 것만 만듭니다. 문제·노트·탐구 주제 테이블은 해당 기능을 만들 때
추가합니다.

### `user_concepts` — 개념별 학습 상태

| 열 | 뜻 |
|---|---|
| `user_id`, `concept_slug` | 복합 기본키 |
| `saved_at` | 내 지식에 추가한 시각 |
| `last_level` | 마지막으로 읽은 난이도 (1~5) |
| `last_studied_at` | 마지막으로 읽은 시각 |
| `understanding` | 이해도. **Phase 7에서 채웁니다. 그전까지 비어 있습니다.** |

저장(북마크)과 진도를 한 행에 둡니다. 둘은 1:1이고 목록 화면에서 늘 함께
필요하므로, 나누면 매번 조인해야 합니다.

`concept_slug`에는 외래키를 걸지 않습니다. 개념 본문은 DB가 아니라 저장소의
JSON 파일에 있습니다. **콘텐츠는 git이, 학습 기록은 DB가 맡는다**는 경계를
유지합니다.

### `stuck_events` — '여기서 막혔어요'

어느 개념 어느 단계의 설명이 부실한지 알려주는 신호입니다. 같은 지점을 여러 번
누를 수 있으므로 이벤트 로그로 쌓습니다. 이 데이터가 그대로 집필 우선순위가 됩니다.

## 5. 브라우저에 쌓인 기록을 잃지 않기

Phase 3에서 이미 저장한 개념이 있는 사용자가 로그인하면, 그 기록을 서버로
합칩니다. 규칙은 이렇습니다.

1. 로컬 저장소를 읽어 서버에 `upsert`
2. 같은 개념이 양쪽에 있으면 **`last_studied_at`이 더 최근인 쪽**을 남김
3. 합치기가 끝나면 로컬 기록에 동기화 완료 표시. 로컬 데이터는 지우지 않음
   (로그아웃 후에도 계속 쓸 수 있어야 하므로)

로그인하지 않은 사용자는 지금과 똑같이 동작합니다. **로그인은 선택이지 강제가
아닙니다.**

## 6. 구현 순서

1. 로그인/로그아웃 화면과 세션 처리
2. `store.ts`에 서버 백엔드 추가 — 화면 코드는 그대로 두고 이 파일 안에서만 분기
3. 로그인 시 로컬 기록 합치기
4. `/my`가 로그인 상태에 따라 서버 또는 로컬을 읽도록 연결
5. 개인정보처리방침 갱신 (계정·이메일·서버 저장 항목 반영)

`store.ts`를 단일 통로로 만들어 둔 것이 여기서 값을 합니다. 화면 컴포넌트는
수정 없이 그대로 갑니다.

## 시작하기 전에 필요한 것

제가 대신 할 수 없는 일입니다.

1. **Supabase 프로젝트 생성** — [supabase.com](https://supabase.com)에서 새 프로젝트를
   만들어 주세요. 리전은 `Northeast Asia (Seoul)`을 고르면 응답이 가장 빠릅니다.
2. **스키마 실행** — 대시보드의 SQL Editor에 `supabase/migrations/0001_init.sql`
   내용을 붙여 넣고 실행합니다.
3. **키를 로컬에 넣기** — `.env.example`을 `.env`로 복사한 뒤, 대시보드
   Project Settings → API에서 URL과 anon key를 채웁니다.
4. **Vercel에도 같은 값 등록** — 프로젝트 설정 → Environment Variables.
5. **Google 로그인을 쓴다면** — Supabase 대시보드 Authentication → Providers에서
   Google을 켜고 안내에 따라 설정합니다.

`.env`는 `.gitignore`에 있어 커밋되지 않습니다. **키를 저에게 채팅으로 보내지
마세요.** 파일에 직접 넣으시면 됩니다.
